# 空白 HA 与设备接入

## 建立最小维护环境

先辨认 HA OS、Container 等安装方式、Core 版本、网络和备份能力。空白实例先通过正常 onboarding 创建用户并设置时区/位置；位置影响太阳事件，不能拿其他家庭的日出时间代入。让用户安全填写账户和机密，不要求贴到聊天、日志或共享文件中。

区分 Agent 在内网电脑执行还是云端执行。前者通常可直接访问 HA 内网；后者需要能到达的受控连接。按已有 Cloud、VPN 或远程访问能力选择，不默认要求公网端口转发，更不要求开放 SSH。

优先使用 HA 官方 **MCP Server**（HA 作为服务端）；不要误装用于 HA 调用外部工具的 MCP client。先查看当前官方文档及目标 HA 实际支持的配置流程、端点和工具列表；不能把上游最新界面套到旧版本。

菜单位置、端点、工具集、只读和管理员选项都必须经现场版本与当前官方文档核对，不预设存在某个管理界面。不同连接 URL 的权限设置可能不同，不能把一个端点的只读保证套到其他端点。用实际 `tools/list` 和无副作用读取验收能力，而非只看集成显示“已加载”。

支持 OAuth2/PKCE 时可优先使用，避免不必要的长期凭据。需要 REST/WebSocket 或客户端不支持 OAuth 时，引导用户在个人资料安全页面创建长效访问令牌，并安全存入该 Agent 的凭据存储。HA 长效令牌继承账户权限，不是细粒度 scope 的只读令牌。说明专用账户与所需权限，设备控制与管理工具的权限要求分别核验；不默认索取全部管理员工具。

先验证身份、站点、版本、读取实体及已暴露范围。Assist 设备控制暴露与 HomeKit 导出过滤互相独立。仅设备控制通常不需要 SSH；需编辑文件时再选择有范围限制的文件通道，记录目录与备份恢复路径。建立一份不含机密的环境说明、连接检验方式、维护入口与变更记录。

官方工具能做什么取决于目标版本和工具集，不承诺它一定能编辑任意文件。未提供管理工具也不能假称“已分析全部自动化”。

## 从少量设备扩展

按需求分批：先接稳定的灯/插座及相关传感器，验证反馈、人工控制与可用性，再加入门锁、窗帘、空调、热水、扫地机等。接入不等于发真实动作；测试运动设备、清扫、投喂或门锁应与用户任务授权相匹配。

| 生态/入口 | 选择依据与能力边界 |
|---|---|
| 小米 Xiaomi Home | 厂商官方维护的自定义集成，按当前安装方式接入，不等同 Core 内置。使用官方授权流程，核对账户区域、家庭、共享权限、网关/中枢及可选 LAN 能力。Wi-Fi LAN 支持不意味着所有蓝牙/Zigbee 都能直连。 |
| 小米 MIoT / Gateway3 等补充 | 先验收现有接入；高级能力缺失时查兼容表、目标型号、固件与所需网关。MIoT 可补充某些扫地机房间和命令；Gateway3 可补充某些网关子设备与本地事件，不等于任意 Aqara/小米网关通用。 |
| Aqara | 按具体型号在 Matter、HomeKit Device、ZHA、Zigbee2MQTT、兼容厂商网关/本地协议间选择。LANLink 需单独核实网关与固件支持。不要把某个 M3 测试结果推广到所有网关。Zigbee 设备不能同时绑定两个协调器。 |
| 美的 | 优先核实 HA 原生 Midea 对型号/协议的支持。当前官方文档区分本地协议 V1/V2/V3 和新 API；V3 可能需要 token/key，不是所有设备只输 IP 即可。读取与设温、模式、风速分别验收。 |
| 石头/其他厂商 | 核对设备使用厂商 App 还是米家、账户区域及集成支持。即使源实体声明 Clean Area，也要实际读到地图、房间并验证映射。 |
| Matter / HomeKit Device | 前者接入 Matter 设备，后者接入 HomeKit 配件；均不同于将 HA 设备导出苹果家庭的 HomeKit Bridge。遵守设备已有 fabric/绑定及 multi-admin 能力，勿默认恢复出厂。 |

保留厂商 App 中现有地图、房间、设备分享和本地绑定。仅在确需迁移配对且用户已授权时才重置设备。

## 接入验收记录

每个物理设备记录主要实体、补充实体、读取来源、命令来源、单位/倍率、反馈延迟、事件形式、local/cloud、依赖及失败方式。至少区分“声明支持”“接口存在”“当前数据有效”“真实动作验证成功”。记录谁负责开/关、分区、告警等能力，避免两套集成同时触发相同自动化。

设备接入后整理区域与命名，才生成业务规则。能力不足时返回具体缺口和替代路径；不为了凑齐模板要求用户购买全套设备。
